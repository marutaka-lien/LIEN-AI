## 0. できたこと（先に4行）

1. 発送エントリー画面に「**発送完了報告CSVを作る**」パネルを追加した。クリックポストの
   「追跡番号入りCSV」を読み込み → 宛先で注文と突き合わせ → **RMSアップロード用の6列CSV
   （Shift-JIS）** をダウンロードできる。
2. 二度流し防止のため、DBに `Order.shippingReportedAt`（空でも可の日時列）を**1列だけ**追加した。
   前回失敗した書き戻しAPI用の項目（`rmsShippingReflectedAt`）とは別物。触っていない。
3. 対象は「**発送待り（300）× この仕組みで未出力**」に限定。変換時に「注文日から180日超」を自動スキップ。
   同じ宛先に複数注文がある等の曖昧なケースは**代表1件だけCSVに出し、残りは画面表示のみ**（マスターが手入力）。
4. 純粋な変換ロジックに**ユニットテスト33件**を追加（全部パス）。既存テストは236件パス・3件失敗
   （失敗3件は前からあるRMSブラウザ操作テストで、今回の変更とは無関係）。

## 1. 画面の使い方（マスター向け）

場所: 左メニュー「発送」→ 発送エントリー画面。「対象者CSVを作成」の下に新パネル。

1. **［最新化］** … RMSから発送待ち注文を取り直す。**変換の前に必ず押す**
   （RMSで手入力して発送済みに進んだ注文を対象から外すため）。押すと「最終同期 hh:mm・変換対象 n件」が出る。
2. **クリックポストからダウンロードしたCSVファイルを選ぶ** ＋ **発送日**を入れる（既定＝今日）。
3. **［変換］** … 突き合わせ結果がプレビュー表示される。
   - **自動マッチ**: 注文1件 ↔ 追跡番号1件で素直に対応が付いたもの。そのままCSVに出る。
   - **代表のみ**: 同じ宛先に複数注文/複数追跡番号。最古の注文＋最初の追跡番号だけCSVに出る。
     残りは「要確認」に出る（マスターがRMSで手入力）。
   - **要確認 / スキップ / 未マッチ**: CSVには出ない。画面で中身を確認できる。
   - プレビュー表の各行にチェックボックス。**RMSで既に伝票番号を入れた注文はチェックを外す**と
     CSVから除外される。
4. **［ダウンロード］** … 6列CSV（Shift-JIS）が保存される。同時に、出力した注文へ「出力済み」の印が付く
   （次回の変換では既定で除外される）。
5. そのCSVを **RMS「データアップロード（発送完了報告データ）」画面へアップロード**する。

## 2. 実装の中身

### DB
- `prisma/schema.prisma`: `Order.shippingReportedAt DateTime?` を追加。
- マイグレーション `20260908023234_add_shipping_reported_at`（`ALTER TABLE "Order" ADD COLUMN "shippingReportedAt" DATETIME;` のみ）。
- `src/server/order/order.repository.ts`: `findShippingReportTargetOrders()` /
  `markShippingReported(ids, date)` / `getTodayShippingReportSummary()` を追加
  （既存の `findCsvExportTargetOrders` / `markCsvExported` と同型）。

### 変換ロジック（純関数・DB非依存・テスト厚め）
`src/server/integrations/rms-shipping-report/`:
- `clickpost-tracking-csv.ts` … クリックポストCSVを読む。Shift-JIS / UTF-8(BOM) 自動判定。
  **列は位置でなくヘッダー名（部分一致）で探す**ため、多少の列順違いでも動く。
  「追跡番号」「郵便番号」「氏名」「住所」の列が見つからなければ警告を返す。
- `address-key.ts` … 突き合わせキー＝`郵便番号7桁 + 正規化氏名 + 正規化住所`。
  正規化＝NFKC＋空白全除去＋ハイフン/ダッシュ類を半角「-」へ統一。注文側は
  `都道府県+市区町村+それ以降` を区切り無し連結してからキー化（クリックポスト側の住所1本に合わせる）。
- `classify.ts` … キー単位で突き合わせ、自動マッチ / 代表 / 要確認 / スキップ(180日超) /
  未マッチ に振り分け、CSVに出す行（自動マッチ＋代表）を注文番号昇順で返す。
  複数送付先の可能性は `rawPayload` の `PackageModelList` を**読むだけ**で検出。
- `upload-csv.ts` … 6列固定・順序固定・Shift-JISでCSVを組む。送付先ID・発送明細IDは空欄。
  配送会社 `1003`（日本郵便）固定。追跡番号にSJIS表現不可の文字が無いかも確認。

### API（前回失敗コードは import していない）
- `POST /api/rms/shipping-report/convert` … プレビュー（DBは変更しない）。
- `POST /api/rms/shipping-report/download` … CSV生成＋出力済み記録。`excludeOrderNumbers` でチェックを外した行を除外。
- `POST /api/rms/shipping-report/sync` … 最新化（`fetchPendingOrders` を待って実行）＋対象件数を返す。
- `GET  /api/rms/shipping-report/summary` … 本日の実績（件数・日時のみ。個人情報なし）。

### 画面
- `src/components/orders/shipping-report-panel.tsx`（新規）。
- `src/components/automation/shipping-entry-workspace.tsx` にパネルを1行追加。

## 3. 安全策（Gate 1 の方針どおり）

| リスク | 対策（実装済み） |
|---|---|
| 既に発送明細がある注文にID空でアップ → 複数個口の二重登録 | 対象を「300 × 未出力」に限定＋変換前 最新化＋プレビューの行チェック外し＋常時警告文 |
| 同じCSVを二度流す → 増殖 | `shippingReportedAt` を記録し、次回以降は既定で除外 |
| 追跡番号↔注文の取り違え（同一宛先） | 代表1件のみ出力＋残りは要確認。代表行に「代表として1件のみ（要確認）」と明示 |
| 住所・宛名の表記揺れ | 正規化で吸収、残りは「未マッチ」へ（CSVには出さない） |
| 180日超 | 変換時に自動スキップ＋画面表示 |
| 5,000行超 | 画面に警告（分割アップロードの案内） |

前回失敗したAPI書き戻し（`reflectTrackingNumber` 等）には一切触れていない。
`rawPayload` は読み取りのみ（発送明細・送付先数の確認）。

## 4. マスターに確認してほしいこと

1. **クリックポスト「追跡番号入りCSV」の実際の列名**。設計時の想定は
   「追跡番号 / お届け先郵便番号 / お届け先氏名 / お届け先敬称 / お届け先住所 / 内容品」。
   ヘッダー名で列を探しているので多少違っても拾えるが、想定と大きく違う場合は
   実物のヘッダー行（1行目）だけを教えてほしい（中身の個人情報は不要）。パーサーを合わせる。
2. **実地テスト**: 少数の注文で 変換→ダウンロード→RMSアップロード まで通し、
   お荷物伝票番号が正しく入るかを確認してほしい。うまくいったら対象範囲を広げる。
3. RMSアップロードでエラーが出た場合は、その**エラーメッセージ全文**を共有してほしい（原因調査用）。
