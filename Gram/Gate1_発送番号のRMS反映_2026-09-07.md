## 0. 結論（先に4行）

1. **作れる。前回失敗したAPI書き戻しより安全。** RMS公式のアップロード画面へ人がCSVを上げるだけ。
2. **アップロード用CSVは6列固定・宛先列なし**。だから「注文番号↔宛先」の対応表が別に要る。**推奨は「発送完了報告用（ダウンロード用）テンプレートをマスターが1回DL」**（＝候補b）。LIENmanager内の取込済み注文データ（候補a）だけでは、送付先ID・発送明細IDが取れず**二重登録事故**を防げないため。
3. **更新パターンが2種類ある。** 未処理の発送待ち注文＝ID空で「送付先1へ新規」。マスターが既に手入力済みの注文＝送付先ID＋発送明細ID必須。両対応が要る。ダウンロード用テンプレならこの2つのIDが取れ、どちらのパターンかを行ごとに自動判定できる。
4. **既存のクリックポスト用CSV部品（Shift-JIS書き出し・文字正規化・手組みCSVパーサー）が流用可。** 前回失敗コードには一切触れずに独立モジュールで追加できる。工数 **M（2〜3人日）**。

## 1. RMS「発送完了報告データ（アップロード用）」CSV 仕様（確定）

出典: 店舗運営Navi 000038913（2025-06-23更新）。

### ヘッダー（1行目・順序固定・改変不可）

| 順 | 列名 | 位置づけ |
|---|---|---|
| 1 | 注文番号 | **必須**。`店舗ID-yyyymmdd-******`。文字列まるごとで照合 |
| 2 | 送付先ID | 条件付き必須。半角数字最大10桁。空 → 「送付先1」に追加登録 |
| 3 | 発送明細ID | 条件付き必須。半角数字12桁。空 → 送付先（未指定なら送付先1）に追加登録 |
| 4 | お荷物伝票番号 | 更新項目。全半角問わず120文字以下。機種依存文字NG。空欄可 |
| 5 | 配送会社 | 更新項目。**数値コード**。**日本郵便 = 1003**。空欄可。ただし既に登録済み情報があるときは空欄で更新不可。RMSで事前設定が必要 |
| 6 | 発送日 | 更新項目。`yyyy-mm-dd` または `yyyymmdd`。空欄可 |

**このCSVには送付先の氏名・住所・郵便番号の列がない。** → クリックポスト出力CSV（宛先あり・注文番号なし）と直接は結べない。

### 制約（設計に明記）

- **文字コード: Shift-JIS 必須**（アップロード画面明記。UTF-8不可）。
- **1回のアップロード上限: 5,000レコード**。
- **注文日を含め180日以内**のみ。181日以上前は不可。
- 1注文あたり送付先IDごとに発送明細20個まで。

### 更新パターン（重要 — 二重登録に直結）

| パターン | 送付先ID | 発送明細ID | 挙動 | 該当する注文 |
|---|---|---|---|---|
| 新規（送付先1へ） | 空 | 空 | 「送付先1」に発送明細を**追加** | 発送待ちで一度も伝票番号を入れていない注文（＝今回の自動化の主対象） |
| 新規（指定送付先へ） | 指定 | 空 | その送付先に発送明細を**追加** | 複数送付先の注文 |
| 登録済み更新 | 指定 | 指定 | 既存の発送明細を**更新** | マスターが既に手入力済みの注文 |

⚠ **既に発送明細がある送付先に、ID空でアップすると「更新」でなく「追加」になり、複数個口（複数レコード）が二重登録される。** ここが最大の事故ポイント。
→ 対策: 橋渡しファイル（§3の候補b）で「その注文・送付先に既に発送明細IDがあるか」を必ず見てから、新規行を出すか更新行を出すかを決める。IDが取れない候補aだけでは、この判定ができない。

### 配送会社コード（抜粋）

`1000`その他 / `1001`ヤマト運輸 / `1002`佐川急便 / **`1003`日本郵便** / `1004`西濃運輸 / `1017`EMS / `1028`Rakuten EXPRESS / `1029`日本郵便 楽天倉庫出荷 / `1030`ヤマト運輸 クロネコゆうパケット …

今回はクリックポスト発送 = **日本郵便 = `1003` 固定**で出す前提。ただし「指定できる配送会社はRMSで事前設定が必要」なので、**RMS店舗設定に日本郵便が登録済みか**をマスターに確認する（§5 質問1）。

### 流用できるもの（新規実装を減らせる）

| RMS CSVのブラウザ自動DL前例 | `LIENmanager\src\server\automations\rms-review-sync\orchestrator.ts` ほか | レビューCSVはブラウザ操作で自動DLしている。**将来**、橋渡しテンプレの自動DLも同じ仕組みで可能（今回のスコープ外・§4） |

### 取込済み RMS 注文データに送付先はあるか（候補a の可否）

`LIENmanager\src\server\integrations\rms\rms-order-mapper.ts` / `prisma\schema.prisma` / `rms-types.ts` を確認:

- **送付先の氏名・郵便番号・住所は取込済み**。`Order.recipientName` / `postalCode` / `prefecture` / `address1`(市区町村) / `address2`(それ以降) に、getOrder の `PackageModelList[0].SenderModel` から入る（無ければ注文者情報にフォールバック）。
- 発送待ち（orderProgress=300）と注文確認待ち（100）が同期対象（`RMS_PENDING_ORDER_PROGRESS_LIST`）。マスターが今使っている「対象者CSVを作成」も orderStatus=300 の注文がDBにある前提で回っているので、**発送待ち注文は実運用上DBに入っている**。
- **ただし候補a には次の穴がある:**
  1. **送付先IDも発送明細IDも取込対象外**（`Order` にそのフィールドがない。`basketId` は rawPayload の中にはあるが型として保持していない。発送明細ID＝shippingDetailId は「初回は存在しない」という理由で送信もしていない）。→ 候補a だけだと「送付先1へ新規」パターンしか作れず、**登録済み更新ができない／二重登録を防げない**。
  2. **複数送付先の注文は先頭1件しか持っていない**（mapper に明記）。複数送付先の注文で誤マッチする。
  3. `postalCode` は `"150-0001"` の形（zip1-zip2 をハイフン結合）。正規化で数字だけにすれば吸収可。
  4. 住所が都道府県／市区町村／それ以降で分かれている。連結してからクリックポスト側と比較する必要（クリックポスト側は区切り無し連結の1本 = `clickpost-mapper.ts` 参照）。

### 前回失敗した API 方式のコード範囲（今回は触らない）

`rms-service.ts` の `reflectTrackingNumber()` ／ `rms-api-client.ts` の `updateOrderShipping` ／ `rms-types.ts`（updateOrderShipping系の型）／ `src\app\api\rms\reflect-tracking\route.ts` ／ `order.repository.ts` の `updateTrackingInfo()` ／ `src\components\orders\copy-tracking-number-button.tsx` ／ Prisma `Order.trackingNumber`・`Order.rmsShippingReflectedAt`。
→ 新機能はこれらを import しない独立モジュールで追加。Prisma スキーマ変更なし（DBに書かない）。

## 3. 突き合わせ設計（「注文番号↔宛先」の橋渡しを含む）

### 橋渡しファイルの候補と推奨

| | 候補a: LIENmanager取込済み注文データ | 候補b: 「発送完了報告用（ダウンロード用）」テンプレをマスターがDL |
|---|---|---|
| マスターの手数 | 追加DL不要 ◎ | RMSの同じ画面で1回DL（今の作業導線内。数十秒） |
| 注文番号↔宛先 | ○（発送待ち注文の氏名/住所/郵便番号あり） | ◎（注文番号＋宛先。送付先単位の行） |
| 送付先ID・発送明細ID | **取れない ✗** | **取れる ◎**（これが更新パターン判定と二重登録防止に必須） |
| 複数送付先の注文 | 先頭1件のみ ✗ | 送付先ごとに行がある ◎ |
| データの鮮度 | 最後の同期時点 | ダウンロード時点（最新） |

**推奨: 候補b を主軸。** 理由:

- §1の⚠のとおり、**ID空でアップロードすると既存発送明細に二重登録する**。これを防ぐには「その注文・送付先に発送明細が既にあるか」をアップロード前に知る必要がある。その情報（送付先ID・発送明細ID）が入るのは候補bだけ。
- 複数送付先の注文も候補bなら送付先ごとの行で正しく扱える。
- マスターの追加操作は「発送完了報告データ（アップロード用の元になるダウンロード用テンプレ）」を1回落とすだけ。手入力1時間 → 数分、の中では誤差。

候補a（DB）は**宛先の補完・クロスチェック用の予備**として使う（例: 候補bの住所表記が崩れている行を、DBの住所で照合し直す）。主キーにはしない。

**未確認（マスターに軽く確認・§5 質問2）:** ダウンロード用「発送完了報告用」テンプレの列に、送付先の**郵便番号・氏名・住所**が入っているか（送付先ID・発送明細IDが取れることは仕様書で確定済み）。入っていない場合は候補aの住所を橋渡しに使う（IDは候補b、宛先は候補a、というハイブリッド）。

### 入力（3点）

- **X: 橋渡しCSV** = 発送完了報告用（ダウンロード用）テンプレ。注文番号 + 送付先ID + 発送明細ID（未登録なら空） + 送付先の宛先。SJIS。
- **Y: クリックポスト出力CSV** = `追跡番号, お届け先郵便番号, お届け先氏名, お届け先敬称, お届け先住所, 内容品`。注文番号なし。文字コードは要自動判定（SJIS濃厚だがUTF-8/BOMも許容）。
- **発送日**（画面入力・既定＝当日。クリックポスト出力CSVに日付列がないため。§5 質問3）。

### 突き合わせキー = 送付先

`郵便番号(数字7桁) + 正規化氏名 + 正規化住所` を連結した文字列。

**正規化（X・Y 両方に同じ処理）:**

1. 空白を全除去（半角/全角スペース、タブ）。
2. NFKC 正規化（全角英数記号→半角、半角カナ→全角カナ、丸数字分解）。
3. ハイフン・ダッシュ類を半角 `-` に統一（`normalizeForClickPostCsv` 流用。全角ハイフン `－`(U+FF0D) も対象に追加）。
4. 郵便番号は数字以外除去で7桁。
5. **住所は X 側の複数列（都道府県/市区町村/それ以降）を区切り無しで連結**してから 1〜3 を適用（クリックポスト側の連結形に合わせる）。
6. 氏名は姓名間スペース除去（1で吸収）。

**あえてやらないこと（誤マッチ防止）:** 漢数字↔算用数字変換、ビル名有無の吸収。ズレた行は「未マッチ」に落として人が見る。

### 行ごとの判定（Xの各行を起点）

橋渡しCSV X の各行（＝注文番号 × 送付先）について:

- **既に発送明細IDがある行** → その注文・送付先は**登録済み**。
  - 既定は「**要確認**」へ（マスターが手入力済みの可能性が高い。勝手に上書きしない）。
  - マスターが「上書きする」を選んだ場合のみ、更新行として出力（送付先ID＋発送明細ID＋伝票番号＋`1003`＋発送日。配送会社は空欄不可なので必ず`1003`を入れる）。
- **発送明細IDが空の行**:
  - Y にキー一致が **ちょうど1件**、かつ Y の追跡番号が空でない → **自動マッチ**。
    出力行 = `注文番号, 送付先ID(Xにあれば転記/なければ空), 空(発送明細ID), 追跡番号, 1003, 発送日`。
  - キーが **X側で複数**（同一宛先に複数注文/複数送付先）または **Y側で複数**（同一宛先に複数追跡番号） → **要確認**（自動反映しない。候補を画面に並べマスターが対応付け）。
  - Y にキー一致なし → **未マッチ（クリックポスト側なし）**。出力に入れない。原因例: 別便（ゆうパック等）、住所表記ズレ、クリックポスト未登録。
- **注文番号の日付（yyyymmvdd 部分）が180日より前** → **スキップ（期限切れ）**。アップロード不可のため出力に入れない＋警告。
- Y にあって X のどの行にもマッチしなかった → **未マッチ（RMS側なし）**。出力に入れない。原因例: 既に発送完了報告済みでDL対象外、別モール、住所表記ズレ。

### 二重反映・二重登録の防止

- 発送明細IDがある行は既定で自動出力しない（上記）。
- ID空の行を新規出力するのは「発送明細IDが空」を X 側で確認できた行だけ（＝§1⚠の事故を構造的に防ぐ）。
- 同じ3入力（X・Y・発送日）をもう一度通しても結果が変わらない（べき等）。

### 出力

- **6列固定・順序固定・Shift-JIS**。ヘッダーは仕様どおり（`注文番号,送付先ID,発送明細ID,お荷物伝票番号,配送会社,発送日`）。
- **1ファイル5,000行まで**。超えたら分割ダウンロード（件数を画面表示。実運用では通常当たらない）。
- 発送日は `yyyymmdd` で出す（RMSはどちらも可、桁欠け事故が起きにくい形）。
- **出力に入れる行 = 自動マッチ行のみ**（推奨）。要確認・スキップ・未マッチは画面に一覧表示するだけ。マスターは確実に通る分だけアップロードし、残りは従来どおり手入力 or 個別対応。
- 伝票番号にSJISで出せない文字が残った行は `findUnmappableCp932Chars` で拾って画面警告（発送は止めない、既存踏襲）。クリックポストの追跡番号は12桁数字なので通常問題なし。

### 処理の並び（擬似コード）

```
X = parseCsv(decodeAuto(fileX))   // 橋渡し（発送完了報告用DLテンプレ）
Y = parseCsv(decodeAuto(fileY))   // クリックポスト出力
Yマップ = groupBy(Y, キー)
Xマップ = groupBy(X, キー)
out = []; 要確認=[]; スキップ=[]; 未マッチX=[]; 未マッチY=[]
for x in X:
  if 注文日(x.注文番号) < today-180: スキップ.push(x, "期限切れ"); continue
  if x.発送明細ID なし == false:            // 既に登録済み
     要確認.push(x, "既に発送明細あり（上書き確認）"); continue
  cand = Yマップ[x.キー]
  if cand なし: 未マッチX.push(x); continue
  if cand.length > 1 or Xマップ[x.キー].length > 1: 要確認.push(x, "宛先が一意でない"); continue
  out.push({ 注文番号:x.注文番号, 送付先ID:x.送付先ID ?? "", 発送明細ID:"",
             お荷物伝票番号:cand[0].追跡番号, 配送会社:"1003", 発送日:yyyymmdd(指定日) })
未マッチY = Y のうち一度も使われなかった行
出力CSV = SJISエンコード(out[:5000])
```

## 4. UI 案

### 置き場所

`LIENmanager\src\app\automation\page.tsx`（発送エントリー画面）の既存「対象者CSVを作成」パネルの下に、新パネル1枚。名称案:「**発送完了報告CSVを作る**」。1画面完結。

### 画面の流れ

1. ファイル入力2つ＋日付
   - 「① RMSからDLした『発送完了報告用』テンプレCSV」
   - 「② クリックポストから出力したCSV」
   - 「発送日」（既定＝当日）
2. ［変換］ → サーバーへ2ファイル送信（`multipart/form-data`）。
3. 結果プレビュー（区分ごとのテーブル）
   - ✅ 自動マッチ（n件）… 注文番号・宛先・入る伝票番号・配送会社(1003)・発送日
   - ⚠️ 要確認（n件）… 「宛先が一意でない」「既に発送明細あり」。第1弾は件数と一覧表示のみ（対応付けUIは第2弾）
   - ⏭️ スキップ（n件）… 180日超
   - ❓ 未マッチ（RMS側n件 / クリックポスト側n件）
4. ［ダウンロード］ → 6列SJISのCSVを保存（ファイル名は日時入り）。
5. マスターが RMS「データアップロード（発送完了報告データ）」へアップロード。

### 実装の分割

- **サーバー**: 新API 1本 `POST /api/rms/shipping-report/convert`（2ファイル受領 → 突き合わせ → 6列SJIS CSV返却。内訳はヘッダー or `?preview=1` で JSON。既存 create-csv の流儀）。
- **突き合わせロジック**: `LIENmanager\src\server\integrations\rms-shipping-report\` に純関数で新設（`parse` / `normalizeKey` / `classify` / `buildUploadCsv`）。DB・ブラウザに触らずユニットテストしやすい。
- **共通化**: `parseCsvText` を `src\server\shared\csv.ts`（仮）へ切り出し両所から使う。
- **クライアント**: 新コンポーネント1つ。DL処理は `create-csv-button.tsx` を参考。
- 既存導線への相乗りはしない（入口＝クリックポストへ送る側、出口＝戻す側で関心が別）。同じ画面に同居のみ。
- 段階実装: **第1弾 = 自動マッチ＋各一覧表示＋ダウンロード**。要確認の手動対応付けUI・登録済み更新モードは第2弾。

## 5. リスク・確認事項

### 楽天の規約・利用条件

- RMS公式の CSV ダウンロード／アップロード画面を人が操作するだけ。API書き戻しも自動ブラウザ操作もしない。前回失敗方式よりリスクが低く、正規手順の範囲内。
- クリックポスト出力CSVはマスター自身のデータ書き出し。LIENmanager は手元の2ファイルを突き合わせて6列CSVを作るオフライン変換のみ。外部送信なし。

### 手戻りしそうな箇所

| 箇所 | リスク | 対策 |
|---|---|---|
| 二重登録（複数個口） | 既に発送明細がある注文にID空でアップ → 追加登録 | 橋渡しに候補b（ダウンロード用テンプレ）を使い、発送明細IDがある行は新規出力しない（構造で防止）。候補aだけの設計にしない |
| ダウンロード用テンプレの宛先列 | 郵便番号/氏名/住所が入るか未確認 | §5質問2。入らなければ宛先は候補a(DB)、IDは候補b のハイブリッド |
| 配送会社の事前設定 | 「日本郵便」がRMS店舗設定に未登録だとアップロード拒否 | §5質問1。未登録ならマスターがRMSで登録 |
| クリックポスト出力CSVの文字コード・列 | SJIS/UTF-8・列順が未確認 | 文字コード自動判定＋ヘッダー行で列位置特定。想定違いは明示エラー |
| 発送日の取得元 | 出力CSVに日付列なし | 画面入力（既定＝当日） |
| 住所表記のズレ | 未マッチがある程度出る | 未マッチ一覧を見せ、その分は手入力。件数が多ければ正規化ルールを追記 |
| 複数送付先の注文 | 送付先の取り違え | 候補b（送付先単位の行）＋宛先マッチで対応。曖昧なら要確認へ |
| 5,000件／180日 | 通常は当たらない | 件数表示で分割案内。180日超は自動スキップ＋警告。注文番号の `yyyymmdd` から判定 |
| 注文番号の末尾ランダム部の重複 | 文字列全体はユニーク | キーは注文番号を文字列まるごとで扱う（末尾だけで判定しない）。既存方針どおり |

### マスターへの質問（新情報で最小化）

1. **配送会社「日本郵便」はRMSの店舗設定に登録済みか？**（「指定できる配送会社はRMSで事前設定が必要」。未登録ならアップロードが弾かれる）
2. **「発送完了報告用（ダウンロード用）」テンプレを1回DLして、列見出し（1行目）を共有してほしい。** 郵便番号・氏名・住所の列が入っているか、送付先ID・発送明細IDの列名を確認したい（中身の個人情報は不要）。
3. **発送日は「画面で1つ入力して全行に適用（既定＝当日）」でよいか。**（クリックポスト出力CSVに日付列がないため）
4. **マスターが既に手入力した注文（発送明細あり）を、この仕組みで上書きするか。** 既定は「要確認」に回して手を触れない案。第1弾は上書き非対応でよいか。
5. **出力CSVは「自動マッチ行だけ」を入れる方針でよいか。**（要確認・未マッチ・スキップは画面表示のみ）
6. 同一宛先に複数注文／複数追跡番号のときは自動反映せず手動一覧に回す方針でよいか（＝大半自動、例外だけ手動）。
