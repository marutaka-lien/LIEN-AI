## 0. 結論（先に4行）

1. **6列CSVは LIENmanager が自前で作れる。** ヘッダーは仕様で固定・既知。送付先ID・発送明細IDは空欄で出し、RMS側で「送付先1へ新規登録」させる。配送会社は `1003`、発送日は画面入力。
2. **橋渡し（クリックポストCSVに注文番号が無い問題）は取込済み注文データで解決。** 送付先ID・発送明細IDが不要になったので、前回の懸念（DBにIDが無い／二重登録を防げない）は**対象を絞れば消える**。
3. **安全の肝は「対象注文の絞り込み」と「べき等」。** 対象 = 発送待ち（orderStatus=300）× この仕組みで未出力 ×（ベストエフォートで）RMSに発送明細なし。同じバッチを二度流しても増殖しないよう、出力済みを記録する小さなDB項目を1つ足す。
4. **マスター質問はほぼ解消。残るは「対象注文の判定基準」の最終合意のみ**（§5）。工数 **M（2〜3人日）＋DB項目追加 S**。

## 1. 自前生成する6列CSVの仕様（確定）

出典: 店舗運営Navi 000038913。

### ヘッダー（1行目・順序固定・改変不可。自前で組める）

```
注文番号,送付先ID,発送明細ID,お荷物伝票番号,配送会社,発送日
```

### 各列に入れる値（今回の運用）

| 列 | 入れる値 | 根拠 |
|---|---|---|
| 注文番号 | 取込済み注文の `orderNumber`（文字列まるごと） | 必須。RMSの照合キー |
| 送付先ID | **空欄** | 空 → 「送付先1」に登録。発送明細がまだ無い注文向け |
| 発送明細ID | **空欄** | 空 → 送付先1に**新規追加**。既存があれば更新、無ければ新規 |
| お荷物伝票番号 | クリックポスト出力CSVの `追跡番号` | 120文字以下・機種依存文字NG。12桁数字なので問題なし |
| 配送会社 | `1003`（日本郵便） | マスター確認済み: RMS店舗設定に登録済み |
| 発送日 | 画面入力の日付を `yyyy-mm-dd` で全行に | クリックポスト出力CSVに日付列がないため。マスターOK |

### 「送付先ID・発送明細ID を空で出す」の安全性検証（仕様＋コード）

**仕様（000038913）:**
- 送付先ID・発送明細IDの両方が空 → 「送付先1」に発送明細を**追加登録**。
- ⚠ **既に発送明細情報（発送日など）が登録されている送付先に、ID空でアップすると「更新」でなく「追加」になり、複数レコード（複数個口）が二重登録される。**
- つまり「ID空で出す」が安全なのは **その注文・送付先に発送明細がまだ1件も無い場合だけ**。

**この運用での結論:**
- マスター回答#4「手入力済み（発送明細あり）は対象外。触るのは“まだRMSに伝票番号を入れていない発送待ち注文”だけ」。
- よって **対象を「発送明細がまだ無い発送待ち注文」に厳密に絞れば、ID空で出しても二重登録は起きない**。
- ただし **LIENmanager は「RMSに発送明細があるか」を自分のデータだけでは確実には判定できない**（`Order.trackingNumber` / `rmsShippingReflectedAt` は前回失敗したAPI経路用で、現行のGoQ運用では基本的に未設定のまま。RMSの実状態は映していない）。
- → 絞り込みは「複数の弱い条件の組み合わせ＋人の最終確認」で担保する（§3「対象注文の絞り込み」）。

### 制約（設計に明記）

- **文字コード: Shift-JIS 必須**（アップロード画面明記）。
- **1回のアップロード上限: 5,000レコード**（実運用では通常当たらない。超えたら分割DL）。
- **注文日を含め180日以内**のみ。181日以上前は不可 → 注文番号の `yyyymmdd` 部分で判定し、超過行は自動スキップ＋警告。
- 発送日書式: `yyyy-mm-dd`（`yyyymmdd` も可だが `yyyy-mm-dd` で出す）。

### 配送会社コード（参考）

`1000`その他 / `1001`ヤマト運輸 / `1002`佐川急便 / **`1003`日本郵便** / `1029`日本郵便 楽天倉庫出荷 / `1030`ヤマト運輸 クロネコゆうパケット …
今回は **`1003` 固定**。

### 橋渡しに使う取込済み注文データ（候補a）— 詳細と対処

`rms-order-mapper.ts` / `prisma\schema.prisma`:

- `Order.orderNumber` … 注文番号（そのまま出力に使う）
- `Order.recipientName` … 送付先氏名。`"姓 名"`（スペース結合）。**null になり得る**（SenderModelに氏名が無い場合）→ 突き合わせでは `recipientName ?? ordererName` でフォールバック
- `Order.postalCode` … `"150-0001"` 形式（zip1-zip2 をハイフン結合）→ **数字だけ抽出して7桁**に正規化
- `Order.prefecture` / `address1`(市区町村) / `address2`(それ以降) … **3列に分割**。連結してからクリックポスト側と比較
- `Order.orderStatus` … RMSの orderProgress を文字列化（`"300"` = 発送待ち）
- `Order.orderedAt` … 代表選定（同一宛先で最古を代表）に使う

**残る注意点と対処:**

| 注意点 | 対処 |
|---|---|
| 複数送付先の注文は先頭の送付先しか持たない（mapper に明記） | `rawPayload` の `PackageModelList.length > 1` を読んで検出（読むだけ・書き戻しコードには触れない）。検出したら「複数送付先の可能性」フラグ付きで**要確認**へ。代表1件のみ出力（マスター#6の方針） |
| `postalCode` が `"150-0001"` 形式 | 数字以外を除去して7桁に（既存 `normalizePostalCode` と同じ考え方） |
| 住所が3列に分割 | `prefecture + address1 + address2` を**区切り無し連結**してから正規化。クリックポスト側の連結1本に合わせる |
| 宛名・住所の表記揺れ | NFKC＋空白全除去＋ハイフン統一で吸収。クリックポスト登録がGoQSystem経由の場合、住所整形がLIENと違う可能性 → 残った揺れは**未マッチ一覧**へ落として手入力 |
| DBの鮮度 | 変換の直前に `fetchPendingOrders()` で最新化（§3）。最終同期が古い場合は画面で警告 |

## 3. 突き合わせ設計（自前生成版）

### 入力（3点）

- **X: クリックポスト出力CSV** … `追跡番号, お届け先郵便番号, お届け先氏名, お届け先敬称, お届け先住所, 内容品`。注文番号なし。文字コード自動判定（SJIS濃厚、UTF-8/BOMも許容）。
- **注文データ** … LIENmanager 取込済み（候補a）。変換直前に最新化。
- **発送日** … 画面入力・既定＝当日。

### 対象注文の絞り込み（安全の要）

LIENmanager 側で「出力候補」にする注文:

1. `orderStatus === "300"`（発送待ち／AWAITING_SHIPMENT）。
2. **この仕組みで未出力**（新設する `Order.shippingReportedAt` が null。下記「べき等」）。
3. （ベストエフォート）`rawPayload` に既存の発送明細（`ShippingModelList` / `shippingDetailId`）が見当たらない。
   ※ getOrder v3 が発送済み注文でこれを返すかは実装時に実データで確認。返さない場合はこの条件は「参考」扱いにし、4 と 5 で担保。
4. クリックポスト出力CSV X に宛先一致がある（＝実際に発送済み）。X 自体が「発送された注文」の事実上のフィルタになる。
5. **変換の直前に最新同期**（`fetchPendingOrders()`）。手入力済み等でRMSが 500（発送済）へ進んだ注文は 300 フィルタから自然に外れる。
   ※ RMSは発送日翌日早朝に 500 へ進むため、当日中の再実行はこれだけでは弾けない → 2・6 で担保。
6. プレビュー画面に**行ごとの除外チェックボックス**。「RMSで既に伝票番号を入れた注文が混じっていないか確認してください」の警告を常時表示。

### 突き合わせキー = 送付先

`郵便番号(数字7桁) + 正規化氏名 + 正規化住所`。

**正規化（注文データ・クリックポストCSV 両方に同じ処理）:**
1. 空白を全除去（半角/全角スペース、タブ）。
2. NFKC 正規化（全角英数記号→半角、半角カナ→全角カナ、丸数字分解）。
3. ハイフン・ダッシュ類を半角 `-` に統一（`normalizeForClickPostCsv` 流用。全角ハイフン `－`(U+FF0D) も対象追加）。
4. 郵便番号は数字以外除去で7桁。
5. 住所は注文データ側の `prefecture+address1+address2` を区切り無し連結してから 1〜3。
6. 氏名は `recipientName ?? ordererName`、姓名間スペースは 1 で除去。

**あえてやらないこと:** 漢数字↔算用数字変換、ビル名有無の吸収 → ズレた行は未マッチへ。

### 行ごとの判定

キーで注文データ（対象注文のみ）とクリックポストCSVをグルーピングし、キー単位で:

| ケース | 判定 | 出力 |
|---|---|---|
| 注文1件 ↔ 追跡番号1件（1対1） | **自動マッチ** | 1行出力（注文番号 / 空 / 空 / 追跡番号 / `1003` / 発送日） |
| 同一キーに注文が複数 or 追跡番号が複数 | **代表1件のみ**（マスター#6） | 代表 = 最古の受注（`orderedAt` 昇順）× そのキーでCSV上最初の追跡番号 を1行出力。残りの注文・追跡番号は**要確認**一覧へ。代表行は「代表として1件のみ反映（要確認）」と明示。既定ON、画面でOFF可 |
| 複数送付先の可能性あり（rawPayload の PackageModelList > 1） | **要確認**（＋分かる1宛先だけ代表出力） | 上と同じ扱い |
| クリックポストCSVに一致なし | **未マッチ（クリックポスト側なし）** | 出力しない。原因例: 別便、住所表記ズレ |
| 注文データに一致なし（CSV側だけ） | **未マッチ（注文側なし）** | 出力しない。原因例: 既に発送報告済み、別モール、表記ズレ |
| 注文番号の日付が180日超 | **スキップ（期限切れ）** | 出力しない＋警告 |

代表ペアリング（最古の注文 × 最初の追跡番号）は**当て推量**（どの追跡番号がどの注文かは分からない）。マスターが#6で許容済み。念のためトグルで無効化可能にする。

### べき等（二度流しても増殖しない）

- **新設: `Order.shippingReportedAt`（nullable DateTime）**。CSV生成時に、出力に含めた注文へ日時を記録する。
  - `csvExportedAt` / `clickPostRegisteredAt` と同じパターン（`order.repository.ts` に前例あり。追加は小さい）。
  - `rmsShippingReflectedAt`（前回失敗API用）とは**別概念**。混同しないよう名前を分ける。
- 再実行時: `shippingReportedAt` が入っている注文は既定で除外し、「前回出力済み（n件）」一覧に表示。アップロード失敗などで本当に出し直したい場合だけ、チェックを入れて再出力可能。
- リポジトリに `findShippingReportTargetOrders()` と `markShippingReported(ids, date)` を追加（既存 `findCsvExportTargetOrders` / `markCsvExported` と同型）。
- **スキーマ変更を避けたい場合の代替**: 状態を持たず、マスターが同じクリックポストCSVを再投入しない運用に頼る。→ 弱い。推奨しない。

### 「マスターが一部を手打ち後に再実行」した場合

- その注文はRMSに発送明細ができているが、`shippingReportedAt` は付いていない（ツール外の操作のため）。ここで再度ID空で出すと**複数個口の二重登録**。
- 防御:
  - 変換直前の最新同期（500へ進んでいれば外れる。当日中は不十分）。
  - `rawPayload` の発送明細ベストエフォート検出。
  - **プレビューの行ごと除外チェック＋警告**（「手打ちした注文はチェックを外してください」）。これが実務上いちばん効く。
  - 運用手順に「この変換を使う日は、手打ちとの併用を避ける（どちらか一方に寄せる）」を明記。

### 出力

- **6列固定・順序固定・Shift-JIS**。ヘッダーは §1 のとおり。
- 発送日は `yyyy-mm-dd`。
- **1ファイル5,000行まで**（超えたら分割）。
- **出力に入れる行 = 自動マッチ行＋代表行のみ**（マスター#5）。要確認・スキップ・未マッチ・前回出力済みは画面表示のみ。
- 伝票番号にSJIS非対応文字が残った行は `findUnmappableCp932Chars` で拾って警告（12桁数字なので通常発生しない）。

## 4. UI 案

`LIENmanager\src\app\automation\page.tsx`（発送エントリー画面）の「対象者CSVを作成」パネルの下に新パネル1枚。名称案:「**発送完了報告CSVを作る**」。1画面完結。

1. **［発送待ち注文を最新化］ボタン**（`fetchPendingOrders` を叩く。最終同期時刻を表示。古ければ警告）
2. ファイル入力: 「クリックポストから出力したCSV」／ 日付入力「発送日」（既定＝当日）
3. **［変換］** → サーバーへCSV＋発送日を送信
4. 結果プレビュー（区分テーブル）
   - ✅ 自動マッチ（n件）… 注文番号・宛先・伝票番号・`1003`・発送日。**行ごとに除外チェック**
   - 👤 代表のみ反映（n件）… 同一宛先グループ。代表行＋「残りは手打ち」の候補一覧
   - ⚠️ 要確認（n件）… 複数送付先の可能性 等
   - ↩️ 前回出力済み（n件）… 既定除外。再出力チェックあり
   - ⏭️ スキップ（n件）… 180日超
   - ❓ 未マッチ（注文側n件 / クリックポスト側n件）
5. **［ダウンロード］** → 6列SJIS CSV。確定時に対象注文へ `shippingReportedAt` を記録
6. マスターが RMS「データアップロード（発送完了報告データ）」へアップロード

### 実装の分割

- **サーバー**: 新API 1本 `POST /api/rms/shipping-report/convert`（クリックポストCSV＋発送日 → 6列SJIS返却＋内訳JSON）。既存 `fetchPendingOrders` は既存API（`/api/rms/...`）を流用 or 新設。
- **突き合わせロジック**: `LIENmanager\src\server\integrations\rms-shipping-report\` に純関数で新設（`parseClickpostCsv` / `normalizeKey` / `classify` / `buildUploadCsv`）。DB・ブラウザ非依存でユニットテストしやすい。
- **リポジトリ**: `order.repository.ts` に `findShippingReportTargetOrders()` / `markShippingReported()` 追加。Prisma に `Order.shippingReportedAt DateTime?` 追加＋マイグレーション（`csvExportedAt` と同型の小変更）。
- **共通化**: `parseCsvText` を `src\server\shared\csv.ts`（仮）へ切り出し。
- **クライアント**: 新コンポーネント1つ。一覧・除外チェックは `order-list-table.tsx` を転用。
- 段階実装: **第1弾 = 最新化＋自動マッチ＋代表1件＋各一覧＋ダウンロード＋べき等**。要確認の手動対応付けUIは第2弾。

## 5. リスク・確認事項

### 楽天の規約・利用条件

- RMS公式のアップロード画面へ人がCSVを上げるだけ。API書き戻しも自動ブラウザ操作もしない（`fetchPendingOrders` の同期は既存機能で、注文の取得のみ）。前回失敗方式よりリスクが低い。

### 手戻りしそうな箇所

| 箇所 | リスク | 対策 |
|---|---|---|
| 二重登録（複数個口） | 既に発送明細がある注文にID空でアップ | 対象を「300 × 未出力 × 発送明細なし(ベストエフォート)」に絞る＋変換前に最新同期＋プレビュー行除外＋警告。運用で手打ちと併用しない |
| 同じバッチの再流し | ID空で再度出力 → 増殖 | `Order.shippingReportedAt` で出力済みを記録し既定除外（べき等） |
| RMSの発送明細有無を確実に判定できない | LIENのデータに無い | getOrder v3 の `rawPayload` に発送明細が入るか実装時に実データ確認。入らなければ人の確認（プレビュー除外チェック）を主防御に |
| 住所・宛名の表記揺れ（GoQ経由整形） | 未マッチが出る | 正規化で大半吸収。残りは未マッチ一覧 → 手入力。件数が多ければ正規化ルール追記 |
| 複数送付先の注文 | 送付先の取り違え | rawPayload で検出 → 要確認。代表1件のみ（マスター#6） |
| 代表ペアリングの当て推量 | 追跡番号↔注文の対応が誤る可能性 | マスター#6で許容済み。トグルで無効化可。代表行は明示ラベル |
| 5,000件／180日 | 通常当たらない | 件数表示で分割案内。180日超は自動スキップ＋警告 |
| 注文番号末尾ランダム部の重複 | 文字列全体はユニーク | 注文番号は文字列まるごとで扱う（末尾だけで判定しない） |
| DBスキーマ変更 | マイグレーション | `csvExportedAt` と同型の追加1列のみ。低リスク。避けたい場合の代替あり（§3、非推奨） |

### マスターへの質問（ほぼ解消。残り1〜2件）

1. **対象注文の判定基準の最終合意**: 「発送待ち（orderStatus=300）× この仕組みで未出力 ×（分かる範囲で）RMSに発送明細なし」を対象とする。
   - LIENmanager は「RMSに手入力済みか」を完全には判定できないため、**変換前に必ず最新同期する**／**プレビューで手入力済み行のチェックを外す**運用に合意してほしい。
   - この仕組みを使う日は、同じ注文をRMSで手打ちしない（どちらか一方に寄せる）ことに合意してほしい。
2. **出力済みを記録するDB項目（`shippingReportedAt`）を1つ追加してよいか**（再流しの増殖防止のため。既存の同種項目と同じ作り）。

## 6. 触らないもの（再掲）

前回失敗した API 書き戻し方式（`rms-service.ts` の `reflectTrackingNumber`、`/api/rms/reflect-tracking`、`updateOrderShipping`、`Order.rmsShippingReflectedAt`、`copy-tracking-number-button.tsx` 等）には一切触れない。新機能は独立モジュールとして追加し、これらを import しない。`rawPayload` は読み取りのみ利用（発送明細の有無・送付先数の確認）。新規に足すのは `Order.shippingReportedAt` 1列のみ。
