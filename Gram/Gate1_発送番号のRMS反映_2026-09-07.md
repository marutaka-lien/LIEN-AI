## 0. 結論（先に3行）

1. **作れる。しかも前回失敗した方式より安全。** 楽天RMS公式の「発送完了報告データ」CSV を落として、クリックポストの出力CSVと**送付先で突き合わせ**て、伝票番号・発送日を埋めて返すだけ。RMSへは公式のアップロード画面から人が上げる。API 書き戻しは一切使わない。
2. **既存のクリックポスト用CSVの部品（Shift-JIS書き出し・文字の正規化・手組みCSVパーサー）がそのまま流用できる。** 新機能は独立していて、前回失敗したコードには一切触れずに追加できる。
3. **着手前にマスターに1つだけ実物を確認してほしい。** 「発送完了報告データ」テンプレートCSVを1本ダウンロードして、列見出しと「配送会社コード」列の有無・中身を見せてほしい。ここだけは公式マニュアルがログインの内側にあって外から確定できなかった。工数はざっくり **M（2〜3日）**。

## 1. RMS「発送完了報告データ（アップロード用）」CSV の仕様

### 分かったこと（複数の外部情報源で一致。公式マニュアルはログイン内側のため実物で最終確認が必要）

| 項目 | 分かった内容 | 確度 |
|---|---|---|
| キー列 | **受注番号**（楽天の注文番号。文字列まるごとで照合される） | 高 |
| 伝票番号の列 | **お荷物伝票番号**（＝送り状番号／追跡番号を入れる欄） | 高 |
| 発送日の列 | **発送日**（あり。通常購入データには無く、この「発送完了報告データ」だけにある） | 高 |
| 配送会社の指定 | **名称ではなく数値コード**で指定する（「配送会社コード」）。日本郵便は複数の外部記事で「1003」とされるが**出典により揺れがあり、店舗設定にも依存する**ため、実物で要確認。RMSが注文ごとに事前に値を入れて出してくるパターンもある | 中 |
| 必須項目 | 照合と反映に最低限必要なのは **受注番号 ／ お荷物伝票番号 ／ 配送会社コード** の3つ。伝票番号が空だと反映は失敗する | 高 |
| 文字コード | **Shift-JIS 必須**（UTF-8 だと不可。課題ファイルの調査どおり） | 高 |
| 余計な列・行 | 仕様どおりの列構成にすること。余計な列・空行があるとアップロードエラーになりやすい | 高 |
| 反映タイミング | 発送完了報告をしても注文ステータスはすぐには「配送済」に変わらず、**発送日の翌日早朝**に進む | 中 |
| 1回のアップロード上限 | 外部情報では確定できず。ただしマスターの1日の件数（手作業で最大1時間ぶん＝数十〜百数十件程度）ならどの上限にも当たらない見込み | 低 |
| アップロード可能期間 | 外部情報では確定できず。一般には「発送待ちステータスの注文」かつ「受注から一定日数内」に限られる想定。RMS画面の注意書きで要確認 | 低 |
| 1送付先に複数配送になる場合 | 楽天の1注文は複数送付先（＝複数伝票番号）を持てる。多くの外部連携ツールは**「複数送付先の注文は非対応。手動で入れて」**という割り切り。今回も同じ割り切りにするのが安全 | 中 |

### 実物で確定してほしいこと（マスターへの依頼／§5に再掲）

- 「発送完了報告データ」テンプレートCSVを1本ダウンロードし、**1行目（列見出し）**と、可能なら**ダミー1行**を共有してほしい（中身の個人情報は不要、列の並びだけ分かればよい）。
- 特に見たいのは次の3点:
  1. 「配送会社コード」に相当する列があるか。列名は何か。
  2. その列に**最初から値が入っているか**（＝RMSが注文の配送方法設定から自動で埋めてくる）、それとも空か。
  3. 「発送日」の日付フォーマット（例: `2026/09/07` か `20260907` か）。

## 2. LIENmanager 側の既存資産の棚卸し

### そのまま流用できるもの（新規実装を減らせる）

### 注文データ（Order モデル）の送付先項目

`LIENmanager\prisma\schema.prisma` の `Order` と `LIENmanager\src\server\integrations\rms\rms-order-mapper.ts`:

- 送付先は `recipientName` / `postalCode` / `prefecture` / `address1`(市区町村) / `address2`(それ以降) に分けて保持。RMSの `SenderModel` から取り込んでいる。
- ただし **RMSの1注文＝送付先1件しか持てない**（複数送付先は先頭だけ採用、というコメントが mapper にある）。
- **重要**: 今回の突き合わせに **LIENmanager の DB は必須ではない**。RMS からダウンロードする「発送完了報告データ」CSV に受注番号＋送付先が既に入っているので、**2つのCSVファイルだけで完結する**。DB は「クリックポスト側の住所表記を、LIENが過去にクリックポストへ渡したときの形（都道府県＋市区町村＋番地を区切り無しで連結）に寄せる」ための参考にできる程度。まずは2CSVだけで設計し、DB連携は入れない。

### クリックポストへ渡している住所の形（突き合わせ設計に効く）

`LIENmanager\src\server\integrations\clickpost\clickpost-mapper.ts`:

- LIEN → クリックポストのCSVは `prefecture + address1 + address2` を**区切り文字なしで連結**し、20文字ごとに4行へ機械分割している。
- つまりクリックポストが持っている（＝出力CSVに出てくる）住所は「東京都〇〇区△△1-2-3□□ビル101」のような**連結済み1本の文字列**。
- 一方 RMS 側CSVの住所は都道府県／市区町村／それ以降が**別列**の可能性が高い。→ 突き合わせでは **RMS側の住所列を連結してから比較**する。

### 既存のCSV出力導線（クリックポスト「まとめ申込」用。逆方向・入力側）

- API: `LIENmanager\src\app\api\clickpost\csv-export\route.ts`（GET。発送待ち×CSV未出力の注文を SJIS CSV で返す）
- ボタン: `create-csv-button.tsx`

## 3. 突き合わせ設計案

### 入力

- **A: RMS「発送完了報告データ」CSV**（マスターがDL）… 受注番号＋送付先（郵便番号／氏名／住所）＋空の「お荷物伝票番号」「発送日」列（＋場合により「配送会社コード」列）。SJIS。
- **B: クリックポスト出力CSV**（マスターがDL）… `追跡番号, お届け先郵便番号, お届け先氏名, お届け先敬称, お届け先住所, 内容品`。注文番号なし。文字コードは要確認（クリックポストは入力SJIS専用なので出力もSJISの可能性が高い。UTF-8/BOMも自動判定できるように作る）。

### 突き合わせキー = 送付先

`郵便番号(数字7桁) + 正規化した氏名 + 正規化した住所` の3点を連結した文字列をキーにする。

**正規化方針（AB両方に同じ処理を適用）:**

1. **前後・途中の空白を全部除去**（半角/全角スペース、タブ）。
2. **NFKC 正規化**：全角英数記号→半角、半角カナ→全角カナ、丸数字などを分解。
3. **ハイフン・ダッシュ類を半角 `-` に統一**（既存 `normalizeForClickPostCsv` を流用。加えて全角ハイフン `－`(U+FF0D) も対象に含める）。
4. **郵便番号は数字以外を除去して7桁**（既存 `normalizePostalCode` と同じ考え方）。
5. **住所は RMS 側の複数列を区切り無しで連結**してから 1〜3 を適用（クリックポスト側の連結形に合わせる）。
6. 氏名は姓名間スペースを除去（1で吸収される）。

**あえてやらないこと（誤マッチを避けるため）:**

- 漢数字↔算用数字の変換（「一丁目」↔「1丁目」）。やり過ぎると別住所を同一視する事故が起きる。→ ここがズレた行は「未マッチ」に落として人が見る。
- ビル名の有無の吸収。片方に「□□ビル」があって片方に無い場合は別キー扱い。→ 「未マッチ」へ。

### 自動反映の条件（これを全部満たすときだけ自動で埋める）

- キーが **A側で1件・B側で1件**（1対1）。
- A側の当該行の「お荷物伝票番号」が**空**（すでに入っていたら二重反映防止でスキップ）。
- B側の「追跡番号」が空でない。

→ 満たしたら A のその行に `お荷物伝票番号 = B.追跡番号`、`発送日 = 発送日（§後述）`、（配送会社コード列があって空なら）確定コードを入れる。

### 一意にならないケース＝「要確認」一覧へ回す（自動反映しない）

- **同一キーに A が複数**（同じ人が同時期に複数注文）。
- **同一キーに B が複数**（同じ宛先に追跡番号が複数）。
- 上記いずれか片方でも複数なら、その塊はまるごと「要確認」。画面に「この宛先: 注文 n 件 / 追跡番号 m 個」と候補を並べ、**マスターが手で対応付け**る（大半は自動、例外だけ手動、という課題ファイルの方針どおり）。

### 二重反映の防止

- A側「お荷物伝票番号」がすでに非空の行は**上書きしない**（「スキップ（入力済み）」一覧に出す）。
- 同じ2ファイルをもう一度通しても結果が変わらない（べき等）。

### マッチしなかった行の扱い

- **A にあるが B に無い**（RMSは発送待ちだがクリックポストに宛先が見つからない）… 出力では**空欄のまま**。「未マッチ（クリックポスト側なし）」一覧に出す。原因例: 別便（ゆうパック等）で送った、住所表記のズレ、クリックポスト未登録。
- **B にあるが A に無い**（クリックポストにあるがRMS側に該当なし）… 出力に載せない。「未マッチ（RMS側なし）」一覧に出す。原因例: すでに発送完了報告済みでDL対象外、別モールの発送、住所表記のズレ。

### 発送日をどこから取るか（要マスター確認）

マスター提示のクリックポスト出力CSVの列に**日付がない**。案:

- **推奨: 画面で発送日を1つ入力（既定＝当日）し、全行に同じ日付を入れる。** 「その日の注文はその日に処理」という運用実態に合う。
- もしクリックポストの出力CSVに「引受日／登録日」列がある版が選べるなら、それを使う（マスターに確認）。

### 出力

- **ベースは A（RMSのCSV）。列構成・行の並びをそのまま維持し、埋めるのは「お荷物伝票番号」「発送日」（＋空なら「配送会社コード」）だけ。他の列は一切触らない。**
- 文字コードは **Shift-JIS** で書き出し（既存 `buildClickPostCsvBuffer` と同じ `iconv.encode`）。
- **出力に含める行の範囲は2案。マスター/フライデー判断:**
  - 案1（安全寄り・推奨）: **自動マッチした行だけ**を出力。要確認・未マッチは画面に出すだけ。→ アップロードは確実に通る分だけ。残りは従来どおり手作業か、手で埋めて再アップロード。
  - 案2: A の全行を出力（未マッチ行は該当セル空欄）。→ 1ファイルで済むが、空欄行がアップロードエラーの原因になり得る。
- SJIS に出せない文字が残った行は既存 `findUnmappableCp932Chars` で拾って画面警告（発送は止めない、という既存踏襲）。

### 処理の並び（擬似コード）

```
A行 = parseCsv(decodeAuto(fileA))   // RMS
B行 = parseCsv(decodeAuto(fileB))   // クリックポスト
Aマップ = groupBy(A行, キー)
Bマップ = groupBy(B行, キー)
for a in A行:
  if a.伝票番号 not empty: → スキップ一覧
  elif Aマップ[a.キー].length > 1 or Bマップ[a.キー].length != 1: → 要確認一覧
  elif Bマップ[a.キー] なし: → 未マッチ(クリックポストなし)一覧
  else: a.伝票番号 = B.追跡番号; a.発送日 = 指定日; (a.配送会社コード が空なら = 確定コード) → 自動マッチ一覧
Bで一度も使われなかった行 → 未マッチ(RMSなし)一覧
出力CSV = SJISエンコード(案1: 自動マッチ行 / 案2: A全行)
```

## 4. UI 案

### 置き場所

`LIENmanager\src\app\automation\page.tsx`（発送エントリー画面）に、既存「対象者CSVを作成」パネルの**隣（下）に新パネル**を1枚足す。名称案:「**発送完了報告CSVを作る**」。1画面で完結させる。

### 画面の流れ（1画面）

1. **2つのファイル入力**
   - 「① RMSからダウンロードした『発送完了報告データ』CSV」
   - 「② クリックポストから出力したCSV」
   - （＋発送日の入力欄。既定＝当日）
2. **［変換］ボタン** → サーバーへ2ファイルを送る（`multipart/form-data`）。
3. **結果プレビュー**（3〜4セクションのテーブル）
   - ✅ 自動マッチ（n 件）… 受注番号・宛先・入る伝票番号を一覧表示
   - ⚠️ 要確認（n 件）… 同一宛先に複数注文/複数追跡番号。候補を並べる（この画面では手動対応付けまではやらず「この分は従来どおり手入力」で割り切るのも可。段階実装）
   - ⏭️ スキップ（既に伝票番号あり）（n 件）
   - ❓ 未マッチ（RMS側 n 件 / クリックポスト側 n 件）
4. **［ダウンロード］ボタン** → SJIS の発送完了報告CSVを保存。ファイル名は日時入り（既存 `buildClickPostCsvFilename` と同じ流儀）。
5. マスターはそのCSVを RMS「データアップロード（発送完了報告データ）」へアップロード。

### 実装の分割

- **サーバー**: 新API 1本 `POST /api/rms/shipping-report/convert`（2ファイル受け取り → 突き合わせ → SJIS CSV を返す。要確認/未マッチの内訳はレスポンスヘッダー or 別 `?preview=1` で JSON。既存 create-csv の「ヘッダーで件数・警告を渡す」流儀に合わせる）。
- **突き合わせロジック**: `LIENmanager\src\server\integrations\rms-shipping-report\` に純関数で新設（`parse` / `normalizeKey` / `match` / `buildCsv`）。DB・ブラウザに触らないのでユニットテストが書きやすい。
- **共通化**: `parseCsvText` を rms-review から `src\server\shared\csv.ts`（仮）へ切り出して両方から使う。
- **クライアント**: 新コンポーネント `shipping-report-workspace` 的なもの1つ。既存 `create-csv-button` のダウンロード処理を参考に。
- 既存導線への相乗りはしない（入口＝クリックポストへ送る側、出口＝戻す側で関心が別）。ただし同じ発送エントリー画面に同居させる。

段階実装するなら: **第1弾＝「自動マッチ＋未マッチ表示＋ダウンロード」だけ**。「要確認」の手動対応付けUIは第2弾（まずは件数表示＋「この分は手入力してください」で回す）。

## 5. リスク・確認事項

### 楽天の規約・利用条件

- 今回は**RMS公式の CSV ダウンロード／アップロード画面**を人が操作するだけ。API 書き戻しも自動ブラウザ操作もしない。→ 前回失敗した方式より規約リスクは低く、サポート対象の正規手順の範囲内。
- クリックポストの出力CSVはマスター自身のデータ書き出し。問題なし。
- LIENmanager がやるのは「手元の2ファイルを突き合わせて3列目を埋める」オフライン変換のみ。外部送信なし。

### 手戻りしそうな箇所

| 箇所 | リスク | 対策 |
|---|---|---|
| RMSテンプレートの列名 | 実物未確認。列名がコード内の想定とズレると変換が動かない | 着手前に実ファイルで確定（§1・§5末）。パーサーは「1行目のヘッダーを見て列位置を特定」する作りにして、列順変更に強くする |
| 配送会社コード | 日本郵便のコードが出典で揺れる／店舗設定依存／自動で埋まる場合あり | テンプレ実物で確認。**列が最初から埋まっていれば触らない**のが最安全。空のときだけ、確定できたコードを入れる。確定できなければ「配送会社コードは手で入れてください」と画面表示 |
| クリックポスト出力CSVの文字コード・列 | SJIS か UTF-8 か、列が固定かが未確認 | 文字コード自動判定（BOM有無＋SJIS/UTF-8トライ）。ヘッダー行を見て列位置特定。想定と違えば明示エラー |
| 発送日の取得元 | 出力CSVに日付列がない | 画面で日付入力（既定＝当日）。§3 |
| 住所表記のズレ | 「未マッチ」がある程度出るのは避けられない | 未マッチを一覧で見せて、その分は従来どおり手入力。件数が多ければ正規化ルールを追記して改善 |
| 複数送付先の注文 | 1注文＝複数伝票番号は自動化しない割り切り | 「要確認」へ。件数は少ない想定 |
| アップロード上限・可能期間 | 未確認 | RMS画面の注意書きを確認。実運用の件数なら問題にならない見込み |

### マスターへの追加質問（Gate 2 着手前に欲しいもの）

1. **「発送完了報告データ」テンプレートCSVを1本ダウンロードして、列見出し（1行目）とダミー1行を共有してほしい。** 個人情報は不要。特に「配送会社コード」列の有無・最初から値が入るか・発送日の書式を知りたい。
2. **クリックポストの出力CSVに日付列（引受日／登録日）はあるか？** 無ければ「発送日は画面で1つ入力して全行に適用（既定＝当日）」でよいか。
3. **配送会社は日本郵便で確定か。** RMS側で配送方法の設定をしているか（＝テンプレの配送会社コードが自動で埋まるか）。
4. **出力CSVは「自動マッチした行だけ」を入れる方針でよいか**（要確認・未マッチ行は画面に出すがCSVには入れない）。
5. RMSのアップロード画面にある**上限件数・アップロード可能期間の注意書き**のスクリーンショットが取れれば欲しい。
6. **同一宛先に複数注文／複数追跡番号のときは自動反映せず手動一覧に回す**方針でよいか（＝大半自動、例外だけ手動）。
7. 「要確認」の手動対応付けUIは**第2弾送り**でよいか（第1弾は件数表示＋手入力案内で回す）。

### 実装工数のざっくり見積り

| 単位 | 内容 | 規模 |
|---|---|---|
| CSV読み込み（SJIS/UTF-8自動判定・共通パーサー切り出し） | 既存流用が効く | S |
